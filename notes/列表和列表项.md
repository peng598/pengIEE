# 列表和列表项

FreeRTOS List 是带哨兵节点的侵入式双向链表：链表节点嵌入 TCB 等对象，节点通过指针连接，不要求对象在 RAM 中连续。其工程价值在于可以用有限指针操作移除任务、组织就绪队列和延时队列；链表自身并不提供并发保护。

## 从字段理解内核不变量

| 字段 | 作用 | 损坏后的典型症状 |
|---|---|---|
| pxNext / pxPrevious | 双向连接 | 遍历死循环、删除时写入非法地址 |
| xItemValue | 排序或等待相关的数值 | 延时唤醒顺序异常 |
| pvOwner | 由节点回到所属任务/对象 | 切换到错误 TCB、栈指针异常 |
| pxContainer | 标识节点当前所属链表 | 重复插入/移除、计数下溢 |
| uxNumberOfItems | 有效节点数，不包含哨兵 | 空表判断与真实链接不一致 |

对有效节点应满足 next->previous 与 previous->next 都指回自身。一个 ListItem 不能同时插入两个链表；TCB 内通常分别有状态链表项和事件链表项，用不同节点表达“等待对象”和“等待超时”两个维度。

## 操作复杂度与实时性

已知节点的移除通常为 $O(1)$；按 xItemValue 有序插入需要遍历，最坏为 $O(n)$。若已有 100 个延时任务，插入代价随位置和链表长度变化，因此任务数量、超时模式和调度器暂停时间都属于 WCET 评估输入。不要只根据“一次函数调用”判断内核路径恒定耗时。

TickType_t 回绕使直接数值比较不能跨全周期排序。FreeRTOS 使用当前延时链表与溢出延时链表等机制处理唤醒 tick 回绕。应用层若实现类似逻辑，应明确计数位宽和最大超时；32 位、1 kHz tick 的完整回绕约为 49.71 天。

## 链表损坏应如何定位

出现 vListInsert 卡死或 uxListRemove 访问异常时，故障函数常是“发现损坏的位置”，并非“写坏内存的位置”。先检查节点所有者和 container，再核对任务栈边界、越界 memcpy、已删除对象句柄，以及超出 syscall 优先级范围的 ISR 是否调用内核。

调试版可启用内核支持的列表完整性检查字节、configASSERT 和栈检查，并对最早被破坏的链接设置数据写入断点。验收包含高频创建/删除、tick 回绕附近超时、ISR 密集通知和资源超时竞争；应用代码不应直接修改内核链表字段以“修复”运行状态。
