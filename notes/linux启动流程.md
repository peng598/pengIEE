# Linux 平台启动流程与硬件定位

## 从上电到用户空间

典型链路为电源与复位稳定 → Boot ROM 读取启动配置 → 从指定介质加载首级引导 → 初始化时钟/DDR → 后续引导程序 → 内核与设备树 → 根文件系统 → 用户空间。具体是否使用 SPL、TPL、TF-A、U-Boot 以及各镜像位置由 SoC 平台决定。

U-Boot 可以存于 SPI NOR、eMMC、SD 等启动介质，Boot ROM 不一定直接加载完整 U-Boot。DDR 尚未初始化时，早期代码通常使用片内 SRAM；所以“没有串口输出”可能发生在电源、绑带、介质读取或 DDR 之前，不能先认定文件系统损坏。

## 分阶段证据

先测各电源、复位释放、参考时钟与启动绑带，再检查启动介质总线活动。若早期日志可见而 DDR 初始化失败，核对器件组织、时序参数、训练和电源完整性；若内核启动但挂载失败，再检查分区、文件系统、驱动与启动参数。

原笔记中的“短接 eMMC_D0 与 GND 进入 Maskrom”仅适用于部分平台及指定恢复流程。该操作不是通用 Linux 启动方法，可能造成引脚争用；应按具体板卡厂商恢复说明使用测试点、时序和连接方式。

## 验收

保存启动阶段时间戳、完整串口日志、镜像校验值、板卡版本和启动介质型号。覆盖冷启动、热复位、慢电源爬升、掉电恢复和介质异常，确认恢复模式不会破坏可用镜像及设备唯一数据。

## 用阶段边界缩小故障范围

启动定位先找“最后一个可信事件”和“下一事件的前提”。可信事件可以是示波器上的复位释放、ROM 对启动介质的片选、SRAM 阶段写出的 GPIO 标志、DDR 训练完成标志或内核早期日志。日志最后一行不一定就是故障点：串口 FIFO 可能尚未排空，日志缓冲也可能尚未提交。平台允许时，用独立 GPIO 标记关键阶段，先证明时间顺序再解释文本。

| 停止位置 | 优先核对的证据 | 不能直接推出的结论 |
|---|---|---|
| ROM 无介质访问 | 复位、电源、参考时钟、绑带采样和安全启动状态 | 不能仅凭无 UART 输出判定 ROM 未运行 |
| 首级已进入，DDR 前停止 | SRAM 栈、时钟初始化、器件组织及训练日志 | 降低 DDR 频率能启动不证明只是软件参数 |
| 内核解压或大块复制不稳定 | 镜像校验、DDR 压力、供电瞬态、缓存一致性 | 单次镜像校验通过不证明整个内存范围可靠 |
| 根文件系统挂载失败 | root 参数、分区标识、驱动是否内建、介质错误 | 不应先覆盖启动介质破坏故障证据 |

用同一镜像、同一板卡反复比较冷启动与热复位；若只在冷启动失败，应进一步区分温度、放电初态和电源爬升，而不是把“冷启动”当成单一变量。

## 镜像完整性与内存稳定性分开验收

镜像哈希相同说明读取到的字节一致；只有与可信发布值比较才能判断它是否为预期版本，普通哈希也不能替代安全启动签名。分别校验介质读出、搬到 DDR 后及解压前的镜像，可帮助定位损坏发生阶段。DDR 测试应覆盖数据位、地址映射、突发访问、缓存开关和工作温度，且测试程序本身不能覆盖正在执行的代码或栈。

掉电恢复需说明哪些元数据可以更新、写入顺序和恢复选择规则。A/B 镜像系统先验证新镜像，再提交启动选择，最后由成功启动确认；不得在新镜像尚不可用时先破坏唯一旧副本。保存每次试验的板号、电源曲线、镜像哈希、启动介质型号和失败阶段，可区分软件回归、单板焊接异常与批次器件变化。
